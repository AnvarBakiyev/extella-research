Компактность, правки и токены на сложном многошаговом workflow
19 октября 2026 года

Что подтверждено

Подходящий предметный язык действительно сокращает авторский артефакт: один
Policy JSON описывает 32-узловой расчёт заказов, пять языков операций, несколько
ветвей и соединений. Его 111 токенов превращаются в подробный DAG из 1400 токенов
и выполняют ту же бизнес-логику, что самостоятельный Python из 1398 токенов.
Экономия Policy против самостоятельного Python составляет 92,1% токенов и 93,9%
UTF-8 байтов. Новых запросов к платной модели: 0.

Сильный контроль меняет интерпретацию: эквивалентный Python factory занимает
122 токена. Он использует тот же доверенный компилятор и даёт те же результаты,
трассы и счётчики. Между Policy JSON и этим Python всего 11 токенов, или 9,0%.
Основную экономию создаёт готовая предметная абстракция и повторное использование
её реализации. Для этой экономии упаковка CSPL не обязательна.

Полный подробный DAG JSON сам по себе не выиграл у Python. Его 1400 компактных
токенов практически равны 1398 у самостоятельного алгоритма. Python builder
того же графа занимает 878 токенов: повторение id/lang/op/in в JSON имеет цену.
Следовательно, глубина и ширина не гарантируют компактность. Нужен подходящий
уровень языка; слишком подробный промежуточный язык может быть многословным.

Что именно сравнивали

Канон: 32 узла расчёта заказов. Разделение paid/refunded/pending; gross, VIP
скидка, net, ступенчатая комиссия, fulfillment, margin, региональный tax,
settlement; агрегация по регионам; пять left join; резервы, риски, итоговые
суммы и подробные обработанные заказы. Вычисления целочисленные.

1. Полный DSL JSON, читаемый и компактный.
2. Python builder source/filter/derive/group/join/plan, разворачивающий точно
   тот же граф без CSPL. Доверенный источник, не sandbox для чужого Python.
3. Python literal того же DSL и отдельно Python literal уже раскрытого IR.
   Последний содержит схемы и анализ, поэтому не выбран главным авторским
   представлением: его большая длина не считается преимуществом DSL.
4. Предметный Policy v1 с 12 явными параметрами: JSON -> генератор DAG ->
   общий проверяющий компилятор -> исполнитель.
5. Эквивалентный Python make_policy_v1 с теми же 12 явными параметрами и
   тем же компилятором. Совпадают полные результаты, трассы и метрики.
6. Ручной независимый Python business_library: отдельные циклы и региональные
   агрегаты, без импортов DAG/CSPL. Сравнивается бизнес-результат и контракт
   входных данных. Он не воспроизводит универсальные трассы каждого узла.

Размеры одной программы

Представление                     Читаемые токены   Компактные токены   Компактные байты
Полный DAG JSON                         2831               1400              4765
Python builder того же DAG              1146                878              3226
Python literal того же DSL              2141               1423              4875
Python literal раскрытого IR            6693               4324             14645
Предметный Policy JSON                   155                111               287
Python factory того же компилятора       130                122               328
Python business-library wrapper          150                130               377
Самостоятельный Python алгоритм         1511               1398              4696

Оба формата показаны, чтобы не сравнивать минифицированный JSON только с
красиво отформатированным Python. Python compact сохраняет AST, строки,
имена и алгоритм; комментарии удалены, отступы сокращены. Это не code golf.
Например, читаемый Policy JSON длиннее читаемого Python factory по токенам
155 против 130, хотя компактный JSON немного короче: преимущество зависит
и от сериализации. Токены и байты — разные метрики.

Проверки смысла

Базовый workflow и восемь независимых изменений проверены на 60 закреплённых
входах каждый: 540/540 пар «политика × вход» совпали с независимым Python.
Набор включает пустой ввод, нули, отсутствие оплаченных заказов, пороги,
целочисленное округление, максимальные значения, смешанные статусы и 50
воспроизводимых seeded-наборов до 256 записей. Это один домен и один корпус,
а не 540 независимых бизнес-задач.

Для каждой пары проверены 16 сохранённых форм представления. Формы, вызывающие
общий DAG, совпадают целиком, включая trace и metrics; ручной oracle совпадает
по result. Эти повторы одного расчёта не считаются независимой статистикой.

Редактируемость: что измерили, а что нет

Восемь изменений: VIP скидка, порог комиссии, маршрут статуса pending вместо
paid, добавление вывода VIP-заказов, параллельная ветка дорогой доставки,
коэффициент возвратного резерва, две налоговые ставки, четыре параметра
комплексной политики. Изменения применялись отдельно к одному baseline.

Число изменённых скалярных полей:
  Одиночные правила: по одному в Policy и подробном DAG.
  Налоговые ставки: два в обоих.
  Комплексная политика: четыре в обоих.
  Параллельная ветка: одно в Policy и девять в раскрытом DAG.

Последний эффект полезен: предметная настройка локализует изменение, а
компилятор строит согласованную ветку и добавляет её в outputs. Тот же эффект
есть у Python factory с таким параметром. Ветка была реализована заранее;
это не доказательство добавления совершенно нового алгоритма одним числом.

Это характеристика конкретных фиксированных форматтеров, а не трудозатраты
человека или надёжность LLM. Длинная строка Python builder делает строковый
patch больше при изменении одного числа. Точные diff-файлы сохранены;
символьные diff имеют указанную в results.json процедуру и не выдаются за
математически минимальное edit distance. Улучшение качества генерации и
скорость человеческого редактирования в этой серии не измерялись.

Глубина и ширина: отрицательный контроль

Проверены 8 синтетических семейств, 8/16/32/64 узла, по 60 входов; отдельные
обычные Python циклы дали те же бизнес-результаты, 480/480. Для depth каждый
шаг добавляет следующее поле value; для width ветви фильтруют записи. Это
показатели структуры, не восемь реалистичных бизнес-процессов.

Узлы            Deep JSON / Python builder       Wide JSON / Python builder
8                        283 / 177                         283 / 185
16                       594 / 368                         589 / 379
32                      1234 / 768                        1217 / 783
64                      2514 / 1568                       2384 / 1502

Вызов готовой Python loop-функции: 18–19 токенов для любого размера; её общая
реализация посчитана отдельно. Он не даёт generic DAG trace. Повторяющаяся
структура хорошо сжимается циклом или генератором, поэтому простое добавление
глубины может ухудшить соотношение размеров явного DAG к Python.

Общая реализация и амортизация

Считаем доставляемый исходный код, включая общую реализацию один раз, затем
N артефактов. Это не автоматически объём prompt: установленный backend вовсе
не обязан передаваться модели на каждом запросе. Исходники здесь конкретные,
не теоретически минимальные; общие module-docstrings оставлены.

Компактные исходники общего стека Policy -> DAG -> engine: 6548 токенов,
23366 байтов. Ручная business-library: 1442 токена, 4936 байтов. Различие
функций явно: общий DAG умеет произвольные графы разрешённого языка и trace,
ручная библиотека поддерживает только это семейство бизнес-правил.

По формуле C_DSL + N*S_DSL < C_Python + N*S_Python:
- Против многократной доставки самостоятельного Python: с шестого артефакта
  по токенам и байтам. До этого начальная цена компилятора больше экономии.
- Против общей ручной business-library: только с 269-го артефакта по токенам
  или с 205-го по байтам при данных реализациях/обёртках.
- Против эквивалентного Python factory того же движка общая реализация одна
  и та же; экономия — только 11 токенов и 41 байт на компактную конфигурацию.
- Подробный DAG JSON не догоняет Python builder в этой серии: на каждый
  артефакт JSON на 522 токена больше, а helper-library builder — 281 токен.

Документация authoring contract также имеет цену: POLICY_LANGUAGE.txt —
275 токенов, PYTHON_FACTORY.txt — 325 токенов, с одинаковой описанной
бизнес-семантикой. Это написанные нами инструкции, не доказанные минимальные
prompts или доказательство способности модели правильно работать по ним.
Промпт-инструкции, входная задача, output, caching и тарифы нужно считать
отдельно в последующем реальном LLM эксперименте. Здесь нет заявлений о
фактическом списании, задержке или точности генерации.

Что это говорит о трёх предположениях

Компактность и токены подтверждены условно: для предметного Policy, который
выражает готовую богатую семантику, выигрыш против полного самостоятельного
кода большой. Для подробного DAG его нет; с сильным reusable Python-контролем
большая часть выигрыша совпадает. Требуется достаточное число повторных задач,
чтобы окупить разработку/поставку компилятора; труд разработки мы не измеряли.

Безопасность не следует из размера. JSON допускает лишь параметры нашего
проверяющего компилятора и не является произвольным Python. Но это свойство
конкретного admission boundary и доверенного компилятора. Безопасность
компиляторов, эффектов и native CSPL исследуется в отдельной части лаборатории.
Данный экономический опыт вообще не использует native CSPL-загрузку.

Дополнительная практическая возможность — несколько уровней абстракции:
Policy -> типизированный DAG -> исполнитель. Человек или модель работает с
12 параметрами, а подробный граф остаётся доступным для статического анализа,
трассировки и проверки зависимостей. Это совместимо с CSPL-on-CSPL, но
эквивалентные обычные Python функции доказательно выполняют ту же композицию.
Именно native интеграцию должен обосновывать отдельный опыт.

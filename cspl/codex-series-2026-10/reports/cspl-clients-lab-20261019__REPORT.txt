CSPL и независимые клиенты одной программы — 19 октября 2026

Результат
Преимущества CSPL по числу клиентских адаптеров и настроек в этом эксперименте
не обнаружено. Три клиента вызывали одну сохранённую программу в каждом из двух
вариантов, не зная её языка, исходного JSON и обработчика. После смены программы,
языка и отката клиентский код и конфигурация вызова остались прежними в обоих
вариантах. Это результат проверки конкретного контракта, а не доказательство
отсутствия преимуществ CSPL в любых архитектурах.

Наблюдаемое удобство CSPL находится у автора/издателя: сырой JSON сохраняется
в code, ссылка на обработчик — в cspl. Для обычного Python мы использовали
готовый диспетчер и автоматически представимые литералами параметры обёртки.
Диспетчер не переписывался; Python-обёртка при обновлении меняла два литерала.
Такое удобство публикации не следует называть экономией адаптеров потребителей.

Что именно было независимым
1. Существующий коннектор Codex → Extella MCP.
2. Отдельный Python-клиент: subprocess, JSON-lines, собственный цикл RPC.
3. Отдельный JavaScript-клиент, написанный другим агентом по контракту без чтения
   Python-клиента: собственный цикл RPC, идентификаторы, обработка ответов.
Новые клиенты используют один установленный официальный stdio/HTTP-транспорт
Extella 0.3.7, самостоятельно запускаемый в отдельных процессах. Авторизация
остаётся внутри транспорта. Это независимость прикладных клиентов, НЕ трёх
транспортных реализаций, организаций или сторонних продуктов. Оба используют
существующую учётную запись primary. Никакие ключи в эксперимент не копировались.
Штатный UI Extella был осмотрен, но прямой запуск Expert через него не проверен;
он не засчитан как четвёртый клиент.

Честный контроль
Оба маршрута получают строго одинаковые байты JSON и вызывают одинаковый Python
интерпретатор через одинаковый готовый runner.py. Native выбирает обработчик
по cspl, Python — внутри готового dispatch(binding, source). Программы сохранены
в двух private Experts со стабильными именами, по одному на маршрут. Это две
публикации одной семантической программы, а не две независимо разработанные
прикладные реализации. Программы содержат 5 случаев каждая: 3 вычисления и
2 ожидаемых отказа проверки входа. Сложность здесь не предмет проверки:
измеряется независимость клиента от смены языка и программы на сервере.
Python выполняется через обычный fython Extella, а не отдельный веб-сервис.
Иначе транспорт и развёртывание смешались бы с проверяемым механизмом.

Первичная ошибка настройки и поправка
Сначала binding/source были записаны в сохранённые kwargs Expert, а в сигнатуре
Python были пустые значения по умолчанию. get_expert подтвердил сохранение kwargs.
При вызове без params два клиента получили unregistered_handler; журнал показал
Kwargs: {}. Контроль с явными params сработал с тем же SHA исходного JSON.
В исправленном контроле издатель закрепляет binding/source как литеральные
Python defaults через repr; потребитель снова передаёт только имя программы.
Это одна поправка публикации, ни одной поправки клиентов. Первые 4 вызова
(2 успешных native, 2 неуспешных Python) и отдельный успешный контроль сохранены.
Корневая причина и поведение REST/UI отдельно не установлены. Нельзя обобщать
это наблюдение на все API или объявлять Python принципиально непригодным.

Общая инфраструктура не бесплатна и не обнулена:
- Написаны 2 универсальных MCP-клиентских модуля; каждый обслуживает оба маршрута.
  Третий клиент — существующий коннектор, его исходный код нами не измерялся.
- Один общий установленный транспорт для двух новых клиентов. В каждом запуске
  заданы 3 одинаковые настройки: исполняемый Python, путь транспорта, слот primary.
  Версия MCP и тайм-аут — параметры универсального протокола, не настройки DSL.
- В файле запроса по маршруту одно место привязки имени программы и устройства;
  id нужен только для журнала опыта и не передаётся в arguments run_expert.
- Готовый runner, Python runtime и 2 используемые registry bindings уже были
  установлены прошлым опытом на обоих исполнителях; их не меняли и не исключаем
  из архитектурных предпосылок. Native дополнительно требует локального CSPL-
  контейнера каждого обработчика: используются 2 ранее установленных на хост.
- Python требует один универсальный шаблон обёртки и корректного quoting данных.
  Его опубликованный код менялся при смене данных, тело диспетчера — нет.
- Для основной серии нужно по 4 записи публикации (v1/v2/bad/rollback) на маршрут;
  фактически выполнено 9 save_expert, включая начальную поправку Python.
  Созданы только 2 новых private Experts. Нативные обработчики не устанавливались.

Наблюдения
Основная серия: 4 состояния × 3 клиента × 2 маршрута = 24 вызова на Mac.
Дополнительно JavaScript-клиент вызвал оба маршрута на Linux = 2 вызова.
Итого 26: 20 успешных запусков программы и 6 ожидаемых ошибок отсутствующего
обработчика. В успешных запусках 100 случаев: 60 точных числовых результатов и
40 ожидаемых отказов валидации. Получены 10 совпадающих пар CSPL/Python.
С учётом первичной настройки и контроля выполнен 31 run_expert.
Смена v1 → v2 меняла affine1 на tier2; это ревизии публикации с разными языками,
а не изменение семантики под тем же зарегистрированным именем языка.

Классификация ошибок с учётом уточнения пользователя:
CSPL с неизвестным handler вернул [Execution Error] 'str' object is not callable.
Python вернул {'ok': False, 'error': 'unregistered_handler'} из нашего диспетчера.
По уточнению пользователя первое сообщение в этом контексте означает, что
хэндлер не зарегистрирован. Это согласуется с постановкой опыта: в фазе bad
мы намеренно указали отсутствующее имя обработчика. Таким образом, оба маршрута
отказали по одной причине. Это не сбой зарегистрированного CSPL-хэндлера и не
доказательство преимущества Python по надёжности. Уточнение относится к этому
пути Extella; само сообщение TypeError вне этого контекста может иметь иной смысл.
Все эти ответы имели внешний isError: false. Нельзя считать успехом только
успешный MCP-вызов или код выхода клиентского процесса. Разница здесь в формате
сообщения об одной и той же ошибке, а не в способности исполнить программу.
У всех трёх клиентов наблюдение повторилось. Откат восстановил v1 у всех трёх.
Итоговый счёт клиентских адаптеров и настроек от этого уточнения не меняется;
регистрация хэндлеров учитывается отдельно как подготовка исполнителей.

Проверка
tests/verify_results.py проверяет точные ожидаемые значения независимо от
удалённого вычислителя, SHA исходных данных и реализаций, реальные журналы
маршрутизации, отсутствие DSL-настроек в вызове, неизменность клиентских файлов,
совпадение ответов клиентов, Linux-исполнение, ошибки и финальный readback.
435 проверок прошли. Замена двух defaults оставляет AST Python-обёртки прежним.
Два клиентских исходника и три файла запросов совпадают с CLIENT_FREEZE.json.
Шаблон Python — 465 байт; опубликованный code: CSPL 352 → 460 байт,
Python 854 → 960 байт. Это только размер поля code, не суммарный размер протокола,
не время разработки и не измерение токенов. Полные размеры записей есть в JSON.
Исходные ответы сохраняются полностью, строки разбираются ast.literal_eval,
а не eval. Тест не доказывает криптографическую достоверность удалённого хоста.

Где преимущество вероятнее всего искать
1. Редакторы/каталоги программ: raw JSON можно валидировать, сравнивать, переносить
   и менять отдельно от обработчика без генерации Python-исходника. В этом опыте
   такая структурная разница показана; экономия трудозатрат ещё не измерена.
2. Чужие уже существующие инструменты публикации, понимающие code+cspl. Тогда
   стандартный формат может заменить договорённости с каждым производителем.
   Нужна проверка независимо выпущенных редакторов/клиентов; два написанных нами
   тестовых клиента этого преимущества экосистемы не доказывают.
3. Большой каталог языков и программ: измерить число publisher-компонентов,
   ошибок quoting, трудозатраты сопровождения и переносимость записей. Контроль
   обязан получить готовый Python-реестр, стандартный манифест и сериализатор.
4. Разграничение прав на публикацию данных и исполнение кода потенциально полезно,
   но ограничения должен обеспечивать сервер. Ни безопасность, ни полномочия
   разных учётных записей в этом опыте не проверялись.

Где выигрыша сейчас нет
Когда независимым потребителям достаточно run(name, params) и готовый диспетчер
уже скрывает язык, реестр и версии, CSPL не уменьшает необходимые клиентские
адаптеры и настройки. Обновление центральной публикации работает в обоих случаях.
Нельзя приписывать CSPL повторное использование, которое даёт сам Extella RPC.

Расход и границы
OpenRouter: 0 запросов. Вызовов LLM для генерации/исправления: 0. Эксперимент
детерминированный. Работа Codex и субагента расходует лимит текущего плана;
серверные внутренние расходы Extella отдельно не измерялись. Не делаем выводов
о скорости: выборка мала, выполнение упорядочено и время включает транспорт.
Разные аккаунты, сетевые разделения, конкурентные публикации, атомарность
обновлений и автоматическая доставка обработчиков здесь не проверялись.

Официальные контракты, сверенные в этой сессии
https://extella.ai/api.html — Expert save: code/cspl/kwargs; run: params/targets.
https://extella.ai/guide.html — раздел 8.6: регистрация собственных обработчиков.
Документация не заменяет сохранённые результаты эксперимента и не подтверждает
предполагаемую автоматическую доставку. Известные ограничения прошлых лабораторий
не исправлялись и не скрывались.

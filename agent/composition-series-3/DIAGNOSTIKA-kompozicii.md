# Диагностика: как в Extella устроена композиция

26.10.2026, после серии 3. Только чтение: установленный SDK (extella-disnet 1.0.1, extella-listener 1.2.5), официальный гид https://extella.ai/guide.html, справочник API https://extella.ai/api.html, OpenAPI платформы, список инструментов MCP, приложение Extella на Mac. Код не менялся, прогонов и проб не было.

## Короткий вывод

**Композиция в Extella есть, и не одним способом. В серии 3 мы взяли единственный недокументированный путь, а документированные пропустили.** Поэтому вывод серии 3 «штатного пути композиции нет» неверен. Верно другое: «мы не использовали документированные пути и не проверили, удобнее ли они».

## Что нашли

| Механизм | Что это | Где описан | Использовали в серии 3 | Классификация |
|---|---|---|---|---|
| Оркестратор `cspl=nohup` | скрипт без функции, вызывает других экспертов через REST; ключ берётся из хранилища KV: `kv_get('extella_api_token')` | гид, разделы 4.1 «NESTED» и 8.4 | нет | документировано, мы не нашли вовремя |
| `parallel_task` + `wait_tasks` | параллельный запуск экспертов и барьер ожидания | гид, разделы 7 и 8.4.1 | нет | документировано |
| Пайплайны `/api/pipeline/save`, `run`, `get`, `list`, `search` | граф из блоков и связей (`startID`, `endID`, `sourceHandle`, `targetHandle`), запуск одним вызовом на выбранном устройстве, семантический поиск | справочник API | нет | есть в API; формат блоков не описан; в аккаунте нет ни одного пайплайна; в приложении на Mac и в MCP пайплайнов нет |
| `Disnet.run(container_path, …, target=None, wait=True)` и `ParallelTask` | публичные методы SDK: запустить зарегистрированный контейнер локально или на другом устройстве | в SDK есть, в гиде не описаны | нет | есть, не документировано |
| `Disnet.send(target, wait)` | отправить функцию задачей на устройство и ждать результата | в SDK есть, в гиде не описано | нет | есть, не документировано |
| `extella_listener.executor.run_container` | внутренняя функция исполнителя слушателя | нигде | **да**, в `k3_chain` и `k3_rulebook` | внутренний путь |
| `$extens('файл')` | подставляет файл из пакета слушателя (например `include.py`) | гид, раздел 4.2 | косвенно | подключение служебного кода, не композиция программ |
| «Каждый обработчик может использовать другие обработчики» | утверждение гида без указания способа | гид, раздел 8.7 | — | заявлено, способ не назван |

## Ответы на пять вопросов

1. **Есть ли штатный публичный механизм вложенных и рекурсивных вызовов?** Для экспертов да: оркестратор `nohup` через REST с ключом из KV, плюс `parallel_task` и `wait_tasks`. Для цепочек есть пайплайны в API. Для обработчик→обработчик документированного способа нет. В SDK есть публичный `Disnet.run`, но в гиде он не описан.
2. **Почему мы их не использовали?** Мы не прочитали гид до проектирования серии. Мы опирались на свой прошлый вывод «ключ эксперту не передаётся» и на находку Codex с `run_container`. Ошибка наша, это вопрос обнаруживаемости и нашей подготовки, а не отсутствия механизма.
3. **Это ограничение SDK, недостающий адаптер или отсутствие механизма?**
   - Для экспертов механизм есть и документирован.
   - Для пайплайнов механизм есть, не хватает описания формата блоков.
   - Для вызова обработчика из обработчика есть публичный метод SDK, не хватает документации и проверки.
4. **Можно ли дать интерфейс без изменения ядра?** Да: тонкий адаптер поверх `Disnet.run` или оркестратор `nohup`. Для пайплайнов нужен только описанный формат блоков.
5. **Что останется недоступным даже после адаптера?**
   - Вложенный вызов через REST идёт через очередь платформы, поэтому несёт её задержку: секунды на звено.
   - Атомарная выкатка новой версии обработчика на несколько устройств не описана.
   - Проверка версии обработчика на устройстве не описана: файлы обработчиков зашифрованы.
   - Это не проверено пробой, только чтением.

## Что дальше, если решим проверять

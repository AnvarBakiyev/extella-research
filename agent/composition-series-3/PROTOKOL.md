# Протокол серии 3: композиция

Черновик от 26.10.2026, до любых прогонов. Прогоны начинаются после «да» Анвара. Изменения после старта пишутся поправками с датой.

## 1. Вопрос

Extella — инфраструктура хранения, композиции, исполнения и распространения. Серия 2 проверила исполнение и распространение, композицию почти не трогала. Вопрос серии 3:

**Что теряем без Extella при сборке программы из частей, если части, их код и языки те же?**

Композиция здесь значит пять вещей:

1. Добавить новый язык.
2. Собрать язык поверх уже существующего: обработчик на обработчике.
3. Соединить программы на разных языках в одну цепочку.
4. Заменить одну часть так, чтобы изменение дошло до всех составных программ.
5. Запустить составную программу на разных машинах.

Как и в серии 2, сравнивается не язык с языком, а платформа с той же сборкой из частей. Python здесь один из языков на обеих сторонах.

## 2. Прогноз, записанный до работы

| Сценарий | Прогноз | Почему |
|---|---|---|
| K1. Новый язык | Extella дешевле: регистрация одним вызовом, язык сразу виден всем программам и машинам | на Python нужен свой механизм подключения и доставка на каждую машину |
| K2. Язык поверх языка | Extella дешевле, если обработчик может вызвать другой обработчик штатно; иначе поровну | не знаем, есть ли штатный путь; это главный открытый вопрос серии |
| K3. Цепочка из трёх языков | поровну по коду, Python быстрее | обе стороны пишут клей; у Extella каждое звено — отдельный вызов через слушатель |
| K4. Замена части в 100 составных программах | Extella дешевле при большом числе программ | одна регистрация против пересборки или перезапуска каждой |
| K5. Та же составная программа на трёх машинах | Extella дешевле: ноль действий на машинах | на Python доставка зависимостей и рантаймов на каждую машину |
| Скорость | Extella медленнее в 10–100 раз на звено | серия 2 |

**Тезис считается подтверждённым** в сценарии, если разница не меньше порога из раздела 6. **Тезис опровергнут,** если разница ниже порога или в пользу Python. Опровержение публикуется так же, как подтверждение.

## 3. Материал

Одна сквозная задача, похожая на работу клиента: **отчёт по заказам**.

1. **Выборка.** Язык `readsql`: только SELECT по базе SQLite с 2000 синтетических заказов. Набор фиксируется seed 20261027.
2. **Расчёт.** Язык `steps` из серии 2: итоги, скидки, налог по правилам; проверки исполнителя включены.
3. **Вывод.** Язык `card`, новый для этой серии: карточки отчёта в HTML, все строки экранируются.

**Язык поверх языка (K2).** Это `rulebook`: правила скидок в виде таблицы. Его обработчик переводит таблицу в план `steps` и отдаёт этот план обработчику `steps`. Логика `steps` при этом не копируется.

Языки и их обработчики пишутся один раз и даются обеим сторонам одинаковым кодом на Python. Сравнивается только то, как части подключаются, соединяются, меняются и доставляются.

## 4. Стороны

- **Extella.**
  - Обработчики регистрируются экспертами-регистраторами, как `gsm_register_steps` в серии 2.
  - Программы на этих языках — эксперты.
  - Цепочка — эксперт, который вызывает экспертов, или последовательные вызовы из оркестратора, смотря что даёт платформа.
  - Машины: Mac, server-1, server-2, у всех слушатель.
- **Сборка из частей.**
  - Языки — пакет Python с точками подключения (entry points).
  - Программы — файлы в git.
  - Цепочка — функция, которая вызывает обработчики по очереди.
  - Удалённое исполнение — стек серии 2: Redis и RQ, ssh-туннель, воркеры. Он уже собран, поэтому его стоимость берётся из описи серии 2 и не считается заново, кроме доработок.
- **Обе стороны строит один исполнитель,** Claude, по приёмочным проверкам из раздела 5. Журналы с отметками времени ведутся так же, как в серии 2.

## 5. Сценарии и приёмка

| Сценарий | Приёмка (одинаковая для обеих сторон) |
|---|---|
| K1. Новый язык `card` | программа на `card` исполняется на Mac и на server-1; модель (Qwen 9B, локально) по описанию языка пишет программу на `card` и она проходит обработчик |
| K2. Язык `rulebook` поверх `steps` | программа на `rulebook` даёт тот же итог, что вручную написанный план `steps`, на 20 наборах правил; изменение в обработчике `steps` (новое правило округления) доходит до `rulebook` без правки его обработчика |
| K3. Цепочка `readsql` → `steps` → `card` | отчёт по 2000 заказам совпадает с эталоном, посчитанным отдельно; ошибка в любом звене возвращается вызывающему с названием звена |
| K4. Замена части в 100 составных программах | новая версия `steps` с проверкой перед заменой: правильная ставится и меняет итоги ровно там, где должна; испорченная останавливается до установки; число действий не растёт с числом программ |
| K5. Три машины | та же составная программа даёт одинаковый отчёт на Mac, server-1 и server-2; считается, что пришлось сделать на каждой машине |

## 6. Метрики и пороги

| Метрика | Порог |
|---|---|
| строки кода без пустых и комментариев, только клей и подключение | не меньше чем вдвое |
| действий на машинах (установка, копирование, перезапуск) | меньше хотя бы на одно на машину |
| службы, которые должны постоянно работать | хотя бы на одну меньше |
| ручные исправления после первого запуска | считаются, порога нет |
| время одного прогона цепочки и одного звена | считается, порога нет |
| для K4: зависимость числа действий от числа программ | постоянное против растущего |

## 7. Что берём из прошлого

- **Язык `steps`** и проверка перед заменой (`check_release.py`) из серии 2.
- **Стек серии 2** на Python для удалённого исполнения. Сейчас он снят, перед работой его поднимают заново, и это не считается новой стоимостью.
- **Опыт 14.10** «один обработчик на 40 программ» и демо-языки `readsql`, `page`, `block` от 29.09. Используются как справка, не как результат этой серии.

## 8. Ограничения, известные заранее

- Обе стороны строит один исполнитель.
- Задача одна и синтетическая.
- Windows не входит.
- Если у Extella нет штатного пути «обработчик вызывает обработчик», K2 на стороне Extella собирается обходным путём. Это записывается как находка, а не скрывается.
- Платформенная модель сейчас недоступна. Модель в серии нужна только в K1, там используется локальная Qwen 9B.

## Поправка 1 (26.10.2026, до прогона K2)

- **Новое правило в `steps` для K2.** Вместо «нового правила округления» берётся новый закон: «переменная `rate` не может быть больше 30, иначе отказ». Правило округления на целых ставках скидки ничего бы не изменило, и проверка распространения прошла бы впустую.
- **Эталон для 20 наборов правил.** Ставки считаются отдельным прямым вычислителем правил, без перевода в `steps`. Так эталон не зависит от проверяемого кода.
- **Как устроена композиция на Extella.** Язык `k3_chain` и язык `k3_rulebook` вызывают другие языки на том же устройстве через функцию исполнителя слушателя `run_container`. Это внутренний вызов, в документации платформы его нет: так же он описан в серии Codex `cspl-architecture` от 26.10. Программы Extella не могут вызывать друг друга через платформу, потому что ключ им не передаётся.

## Поправка 2 (26.10.2026, после первого прогона модели в K1)

Первый прогон: Qwen 9B по описанию языка `card` написала 5 программ из 5 в одну строку («title: … group: … count: …»). Обработчик отклонил все пять на обеих сторонах одинаково, результат в `results_k1_model.json`. Причина в описании: в строке документации `card.py` ключи перечислены в одну строку. Кроме того, сообщение обработчика «a card program needs 'group: <field>'» сбивает с толку, потому что `group` в программе есть.

Второй прогон помечен отдельно (`results_k1_model_v2.json`). В описание добавлен пример программы с одним ключом на строку. Сам обработчик не меняется. Первый прогон не заменяется и остаётся в отчёте.

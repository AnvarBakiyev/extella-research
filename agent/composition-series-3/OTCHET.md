# Серия 3: композиция. Отчёт

26.10.2026. Протокол и две поправки: `PROTOKOL.md`. Журналы с отметками времени: `zhurnal-extella-stek.md`, `zhurnal-python-stek.md`.

## Вопрос

Что теряем без Extella, когда программу собирают из частей, а сами части, их код и языки те же. Сравнивается платформа с той же сборкой из частей, а не язык с языком.

## Короткий ответ

1. **Композиция на Extella работает.** Язык поверх языка и цепочка из трёх языков дают тот же результат, что на Python. Отчёт по 2000 заказам совпал с независимым эталоном на трёх машинах.
2. **Мы собрали композицию через внутренний путь и не проверили документированные.** Обработчик в серии вызывал обработчик внутренней функцией слушателя `run_container`, в документации её нет. Диагностика после серии нашла документированные пути (`DIAGNOSTIKA-kompozicii.md`):
   - оркестратор `cspl=nohup` вызывает экспертов через REST, ключ берёт из хранилища KV;
   - пайплайны в API;
   - публичный метод SDK `Disnet.run`.

   Удобнее ли они Python, серия не проверяла. На Python то же самое — обычный импорт модуля.
3. **Выигрыш Extella — в доставке на машины (K5).** Новой машине хватило двух вызовов платформы и ни одного входа на неё. Машину, куда нет shell-доступа, платформа достала через слушателя, Python-стек туда не поставить. На Python новой машине понадобилось около семи действий по ssh.
4. **В подключении нового языка, смене части в 100 программах и в цепочке Extella не дешевле по коду.** В языке поверх языка и в смене части с проверкой кода у неё больше.
5. **Скорость.** Цепочка через платформу 8–11 с, на Python 0,2–1,2 с.

## Как делали

- **Общий код языков** одинаковый на обеих сторонах, лежит в `langs/`:
  - `readsql` — только SELECT, база открывается на чтение, 16 строк;
  - `steps` — исполнитель серии 2 плюс режим `map`, 137 строк;
  - `card` — отчёт карточками, 32 строки;
  - `rulebook` — правила скидок, переводятся в план `steps`, 33 строки;
  - `chain` — цепочка звеньев, 17 строк.
- **Данные.** 2000 синтетических заказов, seed 20261027. Эталон отчёта посчитан напрямую, без языков: `data/reference.py`. Эталон для 20 наборов правил — отдельный прямой вычислитель: `data/rulesets.py`.
- **Extella.**
  - Языки регистрируются одним экспертом `k3_register_langs` на устройство.
  - Программы — эксперты.
  - `k3_chain` и `k3_rulebook` вызывают другие языки на том же устройстве через `run_container`.
  - Машины: Mac, server-1, server-2.
- **Python.**
  - Языки — модули.
  - Вызов языка — функция `run_lang`.
  - Доставка на машины — scp и ssh.
  - Машины: Mac и server-2. На server-1 shell-доступа нет.
- **Обе стороны строил один исполнитель,** Claude, по приёмке, записанной до работы.

**Пороги из раздела 6 протокола:**
- **Строки кода.** Вдвое меньше ни у Extella, ни у Python нет, кроме K2, где у Python 1 строка против 8.
- **Действия на машине.** У Extella их меньше хотя бы на одно в K1 и K5.
- **Постоянные службы.** Ни у одной стороны их не понадобилось. Python исполнял по ssh, а это требует открытого входящего порта 22 на машине. На машине без входящих портов Python-стеку понадобился бы набор серии 2: Redis, туннель и воркеры.

## Находки

- **Использованный путь композиции не документирован.** Внутри обработчика другой язык вызывается функцией `extella_listener.executor.run_container`. Путь найден по серии Codex `cspl-architecture` от 26.10, работает на том же устройстве. Документированные пути — оркестратор `nohup` с ключом из KV, пайплайны, `Disnet.run` в SDK — в серии не использовались, см. `DIAGNOSTIKA-kompozicii.md`.
- **Ключ эксперту платформа не передаёт сама.** Документированный путь — положить ключ в хранилище KV и читать его оттуда. Наш прежний вывод «эксперт не может вызвать эксперта» неверен.
- **Сломанная цепочка возвращает ошибку звена** одинаково на обеих сторонах. Пример: «link 2 (k3_steps): … name 'vat' is not defined».
- **Исполнитель `steps` падает с необработанной ошибкой Python** на `max()` с одним аргументом вместо понятного отказа. Дефект тянется с серии 2. В серии 3 его обошли переводом в `rulebook`, сам `steps` не меняли.
- **Качество описания языка решает, сможет ли модель на нём писать.** С описанием, где ключи `card` перечислены в одну строку, модель написала 0 программ из 5. С примером по ключу на строку — 5 из 5. Сообщение обработчика «needs 'group'» при программе в одну строку вводит в заблуждение. Из 5 программ, принятых обработчиком, по смыслу верны 4: в «итоге по регионам» модель не поставила `sum: total`.
- **Файлы обработчиков на устройствах зашифрованы.** Какая версия стоит, видно по хэшу, который возвращает регистратор. Отдельной проверки версии на устройстве нет.
- **Доступ.** Платформа исполняет на машине, куда у нас нет shell, если там стоит слушатель. Python-стеку нужен shell на каждой машине. Это главная практическая разница в доставке.

## Что можно утверждать

- **Можно:**
  - «Программы на разных языках собираются в цепочку и язык строится поверх языка на устройстве. Результат тот же, что у того же кода без платформы».
  - «Новую машину Extella готовит двумя вызовами платформы, без входа на машину».
- **Нельзя:**
  - «Композиция на Extella удобнее, чем на Python»: для пути через `run_container` это неверно, документированные пути не проверены.
  - «У Extella нет штатной композиции»: она есть — оркестраторы `nohup`, пайплайны, `parallel_task`.
  - «Композиция на Extella дешевле по коду».
  - «Extella быстрее».

## Ограничения

- Обе стороны строил один исполнитель.
- Задача одна и синтетическая.
- Python-сторона в K5 на двух машинах, а не на трёх: на server-1 нет shell-доступа.
- После K4 на Mac и server-1 стоит `k3_steps` версии 2, на server-2 версии 1. Отчёт K5 от этого не зависит: в нём ставка не выше 18 %.
- Windows не проверялся.

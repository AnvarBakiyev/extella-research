# Точность: проверяемость порченых программ и верность первой попытки с ростом правил

Дата: 20.10.2026. Два замера по вопросу Анвара «как доказать, что на языке задачи точнее». Скрипты `zamer_mutacii.py` и `zamer_scale.py`; сырые данные `results_mutacii_{sonnet,opus}.json`, `results_scale_<модель>_<N>.json`.

## Замер А. Точность как проверяемость: порченые программы

### Установка

Берём правильные программы с 12 правилами из `otchet-long.md` (по одной на модель: Python-функция и программа на `zakaz2`) и портим каждую одинаковыми операторами, по одному месту за раз, перебирая все места:

- DEL: убрать одну строку;
- CMP: перевернуть одно сравнение (`>` ↔ `<`, `>=` ↔ `<=`, `==` ↔ `!=`);
- NUM: изменить одну числовую константу (×10, 0 → 1);
- STR: подменить одну строковую константу другой из той же программы;
- ID: подменить одно имя другим именем той же программы.

Каждую порченую версию проверяем в два шага и смотрим, кто поймал первым:

1. **Статика, до запуска.** У `zakaz2` это проверка обработчика: разбор, все поля результата заданы, все имена определены, типы полей совпадают с объявленными, значения строковых полей из закрытого списка (`маршрут` ∈ {ждать_менеджера, резерв, проверка}, `приоритет` ∈ {высокий, средний, обычный}). У Python: компиляция и pyflakes (синтаксис, неопределённые имена). Проверки типов и закрытых списков у Python нет: функция без аннотаций, и mypy на ней ничего не скажет; это честная разница языков, а не недоработка замера.
2. **Тест: 100 заказов против эталона.** Для Python ловит и исключения во время выполнения.
3. **Тихо:** не поймал никто. Это либо порча, не меняющая поведение (мёртвая защитная ветка), либо меняющая его вне 100 заказов.

### Результат

| Программа | Порченых версий | Поймано до запуска | Поймано тестом | Тихо |
|---|---|---|---|---|
| `zakaz2`, программа Sonnet (13 строк) | 96 | 58 (60 %) | 38 | 0 |
| Python, функция Sonnet (49 строк) | 186 | 70 (38 %) | 113 | 3 |
| `zakaz2`, программа Opus (13 строк) | 97 | 59 (61 %) | 38 | 0 |
| Python, функция Opus (52 строки) | 218 | 92 (42 %) | 121 | 5 |

По операторам (Sonnet; у Opus то же с точностью до единиц):

| Оператор | `zakaz2`: всего / статика / тест / тихо | Python: всего / статика / тест / тихо |
|---|---|---|
| DEL | 13 / 13 / 0 / 0 | 48 / 29 / 19 / 0 |
| CMP | 12 / 0 / 12 / 0 | 11 / 1 / 10 / 0 |
| NUM | 15 / 0 / 15 / 0 | 17 / 0 / 15 / 2 |
| STR | 13 / 6 / 7 / 0 | 36 / 0 / 35 / 1 |
| ID | 43 / 39 / 4 / 0 | 74 / 40 / 34 / 0 |

Тихие версии у Python: порча значения по умолчанию в `dict.get(клиент, 0)` → `1` (ветка не срабатывает, потому что клиент всегда из трёх категорий), порча `else 0` при пустом списке позиций (пустых заказов в данных нет), подмена ключа `"новый"` → `"позиции"` в словаре скидок (у «нового» скидка 0, и `get` с умолчанием 0 даёт то же). Это мёртвый защитный код: он не ошибка сегодня, но при изменении данных сработает иначе, и тест этого не покажет.

### Что это значит

1. **Мест для порчи в 2 раза меньше** (96–97 против 186–218) при той же задаче: столько же в программе на языке задачи мест, где человек или модель может ошибиться.
2. **До запуска ловится 60 % порчи против 38–42 %.** Разница из двух источников: убранная строка в `zakaz2` всегда оставляет поле незаданным (13 из 13), а в Python часто оставляет работающую функцию с другим поведением (19 из 48 дошли до теста); подмена строки в `zakaz2` в половине случаев выходит за закрытый список значений, а Python принимает любую строку.
3. **Тихих версий в `zakaz2` нет**, в Python 3–5: в языке задачи нет места для защитного кода, который на этих данных не срабатывает, поэтому любая порча либо отвергается, либо меняет ответ.
4. Перевёрнутое сравнение и испорченную константу не ловит до запуска ни один язык: это смысловые ошибки, их видит только тест. Здесь языки равны.

### Чего не утверждать

- Что язык задачи «ловит все ошибки»: 40 % порчи видна только по тесту, как и у Python.
- Что 60 % переносится на другие языки задач: закрытые списки и типы полей здесь объявлены человеком для этой задачи; без них статика `zakaz2` ловила бы только незаданные поля и неизвестные имена, то есть примерно столько же, сколько pyflakes.
- Операторы порчи одни и те же, но число версий разное, потому что в Python больше строк и имён; сравнивать надо доли, не штуки.

## Замер Б. Верность первой попытки с ростом правил

### Установка

Генератор (`zamer_scale.py`) собирает 12, 24 или 48 правил из семи заготовок (сумма, порог, ставка по категории клиента, счёт позиций по условию, арифметика от прежних полей, метка по порогу, флаг по списку товаров, конъюнкция флагов) с seed, так что эталон строится автоматически: программа-эталон на `zakaz2` порождается тем же генератором и исполняется обработчиком. 100 заказов те же, что в `zamer_long.py`. Правила однострочные и простые; это важно для чтения результата ниже.

Модели: Sonnet 5.5 и Haiku 5.5 через агента (Sonnet с effort low, Haiku с выключенным thinking: платформа иначе не пропускает), Qwen3.5 9B локально через Ollama (temperature 0.7, без размышлений). Три прогона на ячейку, считается только первая попытка: ошибок из 100 заказов, токены, время. Вторая попытка с сообщением о причине — отдельно, ниже.

### Что это значит

1. **На сильных моделях разницы в верности нет до 48 правил.** Sonnet: 18 из 18 программ верны. Haiku: 17 из 18, единственный провал — форма ответа, не логика.
2. **На слабой модели язык задачи не повышает долю верных первых попыток, а понижает её:** у Qwen 9B на 24 и 48 правилах 0 из 6 программ на `zakaz2` принято против 3 из 6 на Python. Модель, не видевшая язык до запроса, путает его с Python и пропускает аргументы.
3. **Но меняется вид провала.** Все 7 провалов на `zakaz2` — отказ обработчика до запуска, с точной причиной. Из 5 провалов на Python два выполнились и вернули неверные ответы на 52 и 24 заказах из 100: такие ошибки видны только при наличии эталона. Это и есть разница, которую стоит называть словом «точнее»: не «модель реже ошибается», а «ошибка слабой модели на языке задачи не доходит до ответа».
4. **Выход короче в 1,2–2,3 раза**, строк в 2–4 раза меньше у всех моделей; вход больше на грамматику (~280 токенов у Qwen, ~726 у Claude с учётом разных токенизаторов). По сумме токенов на создание Python дешевле на всех ячейках, кроме Qwen 12 и 24 правил. Экстраполяция из `otchet-long.md` («равенство при 15–25 правилах») на порождённых однострочных правилах не подтвердилась: Python здесь тоже пишется строкой на правило.

### Вторая попытка с сообщением о причине

`zamer_scale_repair.py`: для каждого провала ровно один повторный вызов с текстом причины (отказ обработчика, исключение или первый расходящийся заказ).

| Ячейка | Python: было → стало | `zakaz2`: было → стало |
|---|---|---|
| Haiku, 24, прогон 2 | | 100 → 0 |
| Qwen, 12, прогон 3 | 100 → 100 | 100 → 100 |
| Qwen, 24, прогон 1 | 52 → 100 | 100 → 93 |
| Qwen, 24, прогон 2 | | 100 → 100 |
| Qwen, 24, прогон 3 | 24 → 0 | 100 → 0 |
| Qwen, 48, прогон 1 | | 100 → 100 |
| Qwen, 48, прогон 2 | 100 → 0 | 100 → 100 |
| Qwen, 48, прогон 3 | 100 → 100 | 100 → 100 |

Haiku исправил формат с первого замечания. Qwen 9B одной поправкой починил 2 из 5 Python-функций (одну ухудшил: 52 → 100) и 1 из 7 программ на `zakaz2` (ещё одну довёл до 93 ошибок). Пять отказов на `zakaz2` повторились с той же причиной: модель снова пишет `select` с двумя аргументами или синтаксис Python. Грамматика в запросе не содержала ни одного примера программы; для модели, которая видит язык впервые, это, вероятно, главная причина, и это недостаток постановки, а не свойство языка. Проверить это можно вариантом «грамматика с одним примером», он не гонялся.

### Чего не утверждать

- Что язык задачи точнее для сильной модели: нет разницы до 48 правил.
- Что слабая модель хуже пишет на языке задачи вообще: она видит язык впервые в этом же запросе, без примера; одна поправка с текстом отказа картину почти не меняет (1 из 7), пример в грамматике не проверялся.
- Что токены на создание на языке задачи ниже: на этих правилах выше.
- Правила порождённые и однострочные; на ручных правилах с ветвлениями (`otchet-long.md`) Python длиннее в 4 раза, здесь в 1,4–2,3.

# Замер пропускной способности на H200

Цель: токены в секунду открытой модели класса 70B на наших запросах (навык и код на лету для zakaz3 и zakaz12) при батчах 1, 8, 32, 64. Из этого: H200-секунд на прогон, H200-часов на 10 000 и 100 000 прогонов в день, число карт.

## Что нужно от Анвара

1. Аккаунт у поставщика GPU. Предлагаю RunPod (Secure Cloud, H200 SXM 141 ГБ): по открытым источникам на март 2026 около 3,6–4 $/час, точную цену покажет их страница при заказе. Пополнить на 20 $.
2. Ключ API RunPod положить в файл командой (ключ в чат не вставлять):

```bash
mkdir -p ~/.runpod && printf '%s' 'ВСТАВИТЬ_КЛЮЧ' > ~/.runpod/api_key.txt && chmod 600 ~/.runpod/api_key.txt
```

3. Написать «готово». Дальше я создаю под с vLLM, поднимаю модель, гоняю `bench.py`, выключаю под. План: не больше 3 часов карты. Отчёт о расходе — по странице биллинга RunPod после остановки.

## Модель

Qwen3.5-72B-Instruct в FP8 (помещается на одну H200 с запасом под контекст), vLLM, max_model_len 8192. Если на Hugging Face этой сборки нет, беру ближайшую официальную 70B-класса в FP8 и записываю, какую именно.

## Как считается

`bench.py` отправляет запросы способов A и B из `PROTOKOL.md` в vLLM (OpenAI-совместимый `/v1/chat/completions`) с параллелизмом 1, 8, 32, 64 по 50 запросов на точку; пишет токены вход/выход (из `usage`), токены/с по входу и выходу, p50/p95 задержки. Результат → `results_h200.json`, затем в отчёт бенчмарка.

## Оговорки

- Относится к этой модели, этой карте, этому движку и этим запросам; на другие модели и карты не переносится.
- Пики нагрузки и резерв клиент считает сам; мы показываем равномерную нагрузку и запас ×2.
